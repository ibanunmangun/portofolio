# PRD: Aceh Tamiang Flood Context Review

## Product summary

Build a public, evidence-bounded cartographic portfolio case study for the recurring flood event reported in Aceh Tamiang in November 2026.

Working title: **Aceh Tamiang Flood Context Review, November 2026**.

The map communicates a dated *reported impact footprint*. It does not estimate the physical flood extent, water depth, damage totals, evacuation routes, or current response conditions.

## User and purpose

Audience: portfolio reviewers assessing cartographic judgment, public-data handling, and evidence communication.

Primary question:

> Which Aceh Tamiang subdistricts were named in the dated BPBA report as affected by recurring flooding, and what does that administrative footprint mean and not mean?

The case study must help a reader distinguish a reported administrative footprint from a satellite-observed inundation polygon.

## Evidence decision

Use a fixed report snapshot dated **16 November 2026**.

A BPBA report, relayed by Tempo, described flooding in 38 villages across five Aceh Tamiang subdistricts: Kota Kuala Simpang, Kejuruan Muda, Karang Baru, Rantau, and Bendahara. The page will map those five named subdistricts as *reported affected administrative areas*.[1]

A separate BNPB report on 13 November documented flood impacts in Aceh Tamiang, including flooded homes and displacement. It is context for the event, not a source for the five-area snapshot.[2]

No reproducible, event-specific satellite flood-extent layer was identified during feasibility work. Satellite flood products require careful event-specific validation. Sentinel-1 flood mapping can miss or misclassify flooding in urban or densely vegetated areas, and satellite products cannot estimate water depth by themselves.[3]

## Scope

### In scope

- A static GitHub Pages case-study page at `/aceh-tamiang-flood-review/`.
- An interactive map of five named, *reported affected* Aceh Tamiang subdistrict polygons.
- HDX COD-AB Indonesia 2020 ADM3 administrative context geometry, used as dated reference geometry rather than an authoritative legal-boundary determination.
- Local, date-stamped report-footprint GeoJSON generated by a deterministic processing script.
- Visible source, report date, method, uncertainty, and limitations.
- Cartographic detail panel showing whether an area is in the dated report footprint.
- Loading, empty, and error map states.

### Out of scope

- Satellite-derived flood extent, unless a reproducible event-specific source is later verified.
- Flood depth, flow, inundation duration, damage valuation, casualty estimates, evacuation advice, or response prioritisation.
- Village-level geometry unless an authoritative source and report-to-boundary join can be verified.
- Live data, live alerts, or emergency operations functionality.

## Reported footprint

Snapshot report date: `2026-11-16`.

Map the following report-named subdistricts in Aceh Tamiang:

1. Kota Kuala Simpang
2. Kejuruan Muda
3. Karang Baru
4. Rantau
5. Bendahara

Map state vocabulary:

- `Named in 16 Nov report`: administrative unit named in the report footprint.
- `Not named in this snapshot`: other Aceh Tamiang administrative units. This does not mean unaffected.
- `Administrative boundary`: reference context only.

## Cartographic direction

Reading this as: an evidence-led cartographic case study for portfolio reviewers, in a dark field-atlas style, dial **ENERGY 2 / RHYTHM 3 / MOTION 1**.

### Kaidah kartografi applied

- **Purpose and hierarchy:** reported areas are the visual figure. Boundary, settlement, and basemap context recede, because a thematic map should make its focal data layer visually primary.[4]
- **Figure-ground:** a low-saturation land context and thin boundary treatment separate administrative reference geography from the reported footprint.[4]
- **Legend integrity:** legend symbols use the same fill, outline, and label as the map. Only the report footprint and boundary context require explanation.[5]
- **Legibility and accessibility:** text meets WCAG AA contrast. The report footprint uses a warm fill plus outline and label, not color alone. The map has an accompanying text description and keyboard-accessible report list.[6]
- **Simplicity:** no terrain, roads, or generic basemap imagery unless it supports the single question. Extra layers would imply spatial precision the evidence does not provide.[6]
- **Uncertainty as map content:** the map labels the layer as an administrative report footprint, not flood extent. The limitation remains visible near the map and in selection details.[3]

### Visual decisions

- Dark ground preserves the portfolio's established field-workbench identity.
- Warm orange-red is reserved for areas named in the dated report. It signals attention, not severity.
- Muted green-grey boundaries show context without competing with the reported footprint.
- Lime remains reserved for keyboard focus and navigation.
- No animated weather effects, moving water, or emergency styling. Motion remains hover and focus only.

## Data and processing

### Boundary source

Use the locally cached HDX COD-AB Indonesia 2020 ADM3 GeoJSON archive to extract Aceh Tamiang subdistrict reference geometry. This source is used because its geometry and licensing were already validated locally; it is not presented as an authoritative legal-boundary determination.

The process must record:

- source URL, release/version, and local archive checksum;
- source feature fields and spatial reference;
- filter predicate and returned feature count;
- selected report-named administrative areas;
- coordinate, geometry, and property validation;
- raw-input and generated-output checksums with deterministic output verification.

### Report source

The local report-footprint table is a hand-curated transcription of the five subdistrict names stated in the 16 November report. The script must make the source URL, report date, publication date, and exact labels explicit. It must not infer area names from news prose at browser runtime.

### Public outputs

- `aceh-tamiang-admin3.geojson`: local Aceh Tamiang subdistrict administrative context.
- `reported-impact-footprint.geojson`: five report-named subdistrict features only.
- `metadata.json`: method, source URLs, report date, scope statement, counts, and limitations.

Raw remote payloads remain local and ignored. No external API key is required for published assets.

## UI requirements

- Header identifies the page as a report-footprint review, not a flood extent map.
- Legend has exactly two concepts: report-named area and administrative boundary.
- Sidebar or accessible list presents each report-named subdistrict as a keyboard-operable native button.
- Selecting a map polygon or list entry updates a details panel using `textContent`, never `innerHTML`.
- Reset returns to the full report-footprint view.
- Map loading, empty, and error states explain what is happening and what the limitation is.
- Desktop, tablet, and mobile layouts must keep map controls, legend, and list visible without horizontal overflow.

## Required limitations

The page must state all of the following in plain language:

- This page is not an emergency-warning system.
- This page is not a flood-extent map.
- This page does not estimate water depth, damage, or response priority.
- The highlighted polygons are administrative areas named in a dated report.
- An area not highlighted was not named in this report snapshot. It may still have been affected.
- Administrative boundaries are reference geometry and do not trace the edge of floodwater.

## Validation and release gate

Before a PR:

1. Validate GeoJSON geometry, coordinate ranges, required properties, report-date field, state values, and no duplicate administrative IDs.
2. Validate metadata source URLs, report date, process description, limitations, and output feature counts.
3. Confirm all published areas are exactly the five report-named areas.
4. Scan public output for secrets.
5. Parse HTML and check JavaScript syntax.
6. Serve locally and test map loading, error, empty, reset, selection, keyboard focus, list selection, legend, desktop, tablet, and mobile.
7. Apply cartographic hierarchy review: report footprint primary, context secondary, uncertainty visible, legend matches symbols.
8. Run anti-slop Delivery Gate and an independent read-only review.
9. Commit only on a feature branch. Push, PR, merge, and deploy require explicit approval.
